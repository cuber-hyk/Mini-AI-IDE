# AI 临时文件管理与工具调用草稿恢复：讨论记录

这是实施前的讨论快照，保留原始建议和当时的未决事项。最终确认路线已实现并验收，见 `docs/adr/2026-10-12-ai-temp-json-recovery.md` 和 `docs/plans/archived/2026-10-12-ai-temp-json-recovery.md`；下文不是当前执行计划或能力说明。

- 日期：2026-10-12
- 状态：初步讨论，尚未进入实施计划
- 项目：Mini-AI-IDE
- 性质：产品与架构方向记录，不代表已经批准实施

## 一、背景

在使用 Mini-AI-IDE 辅助开发时，观察到两个相互独立但可能共享部分基础设施的问题：

1. AI 在开发过程中已经会主动创建 PowerShell、Python、JavaScript 等临时脚本，但这些文件可能散落在用户打开的项目根目录。
2. AI 有时会输出很长的 mini-ai-tools JSON 工具调用，因引号、反斜杠、换行或其他格式问题导致解析失败，随后重新输出整段内容，浪费时间与 Token，并可能再次出错。

两个问题需要分别设计，不能将第一个问题误解为 AI 不具备将复杂命令写入脚本文件的能力。

## 二、议题 A：AI 临时脚本与中间文件管理

### 2.1 已明确的问题定义

AI 本来就会创建临时脚本文件，并能够使用已有文件编辑工具进行局部修改。现有痛点是临时文件缺少统一存放位置、任务归属和生命周期管理，而不是需要重新发明长命令文件化机制。

临时脚本、调试输出、中间数据等可能污染用户项目根目录，与正式项目文件混杂，存在误提交、任务间文件名冲突和长期积累的问题。

### 2.2 工作目录的边界

拟议的 `.mini-ai-ide/tmp/` 位于用户通过已安装 Mini-AI-IDE 打开的项目工作区之内，而不是 Mini-AI-IDE 应用的安装目录，也不是固定放在 Mini-AI-IDE 源代码仓库。

例如用户打开 `D:\Projects\MyProject` 时，临时工作区可位于 `D:\Projects\MyProject\.mini-ai-ide\tmp\`。

只有当用户将 Mini-AI-IDE 源代码仓库本身作为当前工作项目时，该仓库才可能出现自己的 `.mini-ai-ide/` 工作目录。

### 2.3 初步建议

- 按需创建项目级隐藏目录，而非打开项目就无条件创建。
- 临时目录按会话或任务隔离，避免并行任务互相覆盖文件。
- 由 IDE 向 AI 提供准确的任务临时目录路径，并在工具使用规范中要求临时脚本集中存放。
- 继续保留项目根目录作为需要在项目根目录执行的构建、测试和 Git 命令的工作目录，不应简单地全局修改命令 cwd。
- 正式源代码、正式测试和需要纳入项目的脚本仍放入项目原有结构，不能一律迁入临时目录。
- 不主动搬迁、覆盖或删除用户项目根目录中已有的文件；不根据名称猜测哪些现有文件属于临时文件。
- 可研究临时文件登记、用户可见的清理功能以及 Git 忽略规则，但暂不决定具体策略。

### 2.4 尚未决定

- 临时目录命名和任务层级的最终规范。
- IDE 如何区分、标记或追踪临时文件与正式项目文件。
- 是否以及如何自动添加 Git 忽略规则。
- 任务结束后保留多久、何时清理、是否允许恢复。
- 对不遵守目录约定的 AI 工具调用采取提示、警告还是拒绝策略。

## 三、议题 B：长 JSON 工具调用失败后的局部恢复

### 3.1 问题定义

Mini-AI-IDE 通过网页 AI 输出的 mini-ai-tools JSON 来发起本地工具调用。某次调用可能包含很长的脚本内容或多个请求。即使只有局部 JSON 语法错误，也可能导致完整调用无法解析，AI 被迫重新生成大量重复内容。

需要区分：

- 解析阶段失败：JSON 尚未形成合法工具请求，不能直接执行，也不能直接依赖面向已有项目文件的 apply_changes 修复。
- 执行阶段失败：请求已合法解析并通过必要校验，但脚本或命令自身运行出错；如果脚本已经存为文件，可以使用现有编辑工具局部修改。

本议题重点是前一种情况，即尚未解析成功的原始工具调用如何保留和修复。

### 3.2 初步建议

- 在 JSON 解析前保留 AI 输出的原始工具调用文本，形成可标识的待恢复草稿。
- 在解析失败时返回明确错误，尽可能提供错误位置和相关上下文。
- 探索通过草稿 ID 和受控局部编辑机制修改原始调用，避免重新传输整个 JSON。
- 修复后必须重新进行完整 JSON 解析、协议校验、路径及权限检查，不能以草稿已存在为理由绕过检查。
- 对已经执行过的请求保留状态，避免修复某个请求时重复执行成功的其他请求。
- 与现有错误自动回传机制协调，避免形成互相竞争的重试入口或无限重试循环。

### 3.3 关键边界

- 不应声称现有 apply_changes 已能修改解析失败的工具调用草稿；它目前描述的是文件编辑操作，草稿恢复需另外设计入口或协议扩展。
- 保存草稿不等于批准执行草稿；任何恢复后的请求仍需遵守 IDE 原有权限边界。
- 自动修复不得无依据地猜测会改变行为或安全边界的内容。
- 减少整段重复生成有望降低 Token 和时间消耗，但并不保证每次都能成功修复，也不能保证零额外 Token。
- 是否把原始草稿存入 IDE 应用数据目录、怎样管理保存期限及敏感信息，尚待评估。

### 3.4 尚未决定

- 原始草稿的数据模型、保存位置和生命周期。
- 局部编辑采用文本范围、精确字符串替换，还是其他受控方式。
- 如何稳定定位不合法 JSON 中的错误区域。
- 如何关联草稿、原始批次、请求状态与恢复后的批次。
- 自动恢复与人工介入的触发条件、次数上限和中断行为。

## 四、与现有能力的关系

Mini-AI-IDE 已有 read_file、apply_changes、run_command 等本地工具接口。AI 已能先创建脚本文件，再通过文件编辑工具进行局部修改和重试，因此不应将长脚本文件化当作本次需求的新核心能力。

项目现有相关历史文档：

- `docs/adr/2026-10-09-batch-error-auto-return.md`：涉及工具 JSON 解析失败和执行前整批校验失败的错误回传。
- `docs/plans/archived/2026-10-09-batch-error-auto-return.md`：涉及解析失败自动回传、自动继续次数限制与部分中断边界。

上述机制与本次讨论的草稿局部恢复并不相同。后续进入设计或实施前，须先核实当前代码中的实际行为及状态管理，避免重复实现或破坏既有自动继续规则。

## 五、当前形成的共识

1. 用户项目工作区、Mini-AI-IDE 软件安装位置和 Mini-AI-IDE 源代码仓库必须明确区分。
2. AI 临时文件管理的核心是规范已有临时脚本的存放、归属和清理，而不是要求 AI 从头学习如何生成脚本文件。
3. 长 JSON 解析失败后的原始输出保存与局部恢复是另一项独立能力，不能仅靠统一临时脚本目录解决。
4. 两项能力都应优先复用现有工具、权限和执行状态机制，而非绕过原有信任边界。
5. 暂不修改代码，不自动迁移现有文件，不将上述初步建议直接认定为最终架构决策。
