# ADR-0004：回程采用"用户驱动格式约定 + 只读采集 + 预览后应用"，不授予模型落地能力

## 状态

已接受（accepted）。用户已确认默认动作为 **diff 预览（方案 A）**：写入前必须人工确认。

## 背景

需求文档只描述了**出程**（编辑器 → 网页输入框），而该方向已被 ADR-0003 整体移除——出程完全由用户手动完成。于是**回程成了程序唯一的价值所在**：AI 回复里散落着解释、多个代码块、跨文件片段，人工比对与粘贴才是有实际成本的部分。

外部参照（博主原帖评论）给出的心智模型是"AI 直接把代码生成/写进本地文件"。该模型**在本项目不可采纳**，原因有两条且都是硬的：

1. **技术上一眼假。** 让网页端具备写本地文件的能力，必须给它 Node 能力或注入 JS——**这正是本项目禁止的注入与 Electron 泄漏**，会让"无自动化特征"的目标直接破产。2. **产品上不安全。** 无人确认的自动写盘，一次误覆盖的代价远高于"多点一次确认"。

同时存在一个容易混淆的原则冲突需要就地解决：ADR-0003 规定"程序不向网页写入任何内容"。**该约束只适用于出程**，因为写入输入框是会被风控观察的**输入行为**；回程是**读取**，不产生输入特征，因此允许由一次人工按键完成解析与应用。

## 决策

### 一、契约由用户驱动，程序只负责解析

> 本条款修正了早期表述"契约由我们驱动（载荷头部附带指令头）"。经用户澄清：**提示词由用户自己写，出程由用户手动完成**，程序不得代替用户表达意图。因此格式约定改为**用户的输入习惯**，而不是程序注入的指令头。

1. 程序**不注入任何提示性文本、不注入指令头、不注入格式约定**（与 ADR-0003 的"程序不向网页写入任何内容"一致）。
2. 输出格式由**用户在提示词里自行要求**（例如习惯性地说"用带文件路径的代码块回复"）。
3. 程序只做**解析**：识别代码围栏、提取其中的路径标注、切分为待应用变更。解析器必须能容忍"模型没按约定回复"的情况。
4. 由于出程完全移除，**不存在任何"注入成本"**——程序不向输入框写入一个字符。

### 二、回程只读

回程采集**只读**，不得授予网页视图任何写本地或写文件系统的能力。主采集方式为 preload 暴露的只读接口。

**读取不是伪造输入**——这是回程不违反出程约束的依据，也是本 ADR 与 ADR-0003 的分界线。

### 三、预览后应用（信任边界）

1. **默认只预览，不落盘**：解析结果先以 diff 呈现，用户确认后才写入。
2. **写入必须可撤销**：落盘前保留原内容快照。
3. **不提供"跳过预览直接覆盖"的静默默认路径**；激进模式若日后开放，必须是显式设置，且不得成为默认。
4. 目标路径必须通过 `local-file-access` 的白名单校验；越界或新建文件需用户显式确认。

### 四、失败即降级

解析失败不得静默丢弃：原文完整保留，并明确说明对应块缺失或冲突的元信息。每块只采用自身明确路径和相邻标题，不从其他块、当前文件、复制选区或全文提及猜测。缺失信息阻塞对应块，用户补充后重新采集；其他有效块仍可经预览和显式操作应用。已有文件必须提供原替换范围，新内容长度可不同；新建文件完整写入，范围用于格式一致性。没有明确文件修改元信息的围栏归为只读其他内容，不执行或应用；有修改线索但缺失／冲突时保留警告，不以语言标签判断是否写盘。

### 五、不做自动循环

解析结果不得自动回注给模型，也不得在回复到达后自动触发发送。

## 备选方案

| 方案 | 为什么未采用 |
|---|---|
| 让网页端具备写文件能力（给 Node / 注入 JS） | 摧毁"无自动化特征"目标（本项目的硬边界）；且给页面脚本开放本地能力 |
| 默认直接落盘（"一键"字面实现） | 误覆盖代价高；模型输出不可信时无拦截点 |
| 默认只插入光标处、不碰磁盘 | 最安全但丢失多文件同步价值，退化为普通粘贴 |
| 外部脚本抓取 AI 输出后生成代码 | 需要独立进程与抓取逻辑，且必然引入非浏览器网络/进程特征；与"不跑程序、靠 IDE 设计"的思路相悖 |

## 后果

**正面**：拿到"一键同步"的产品价值，同时把三条不可回退的边界（**契约由用户驱动**、回程只读、应用需预览）钉死；程序不写任何提示性文本，人机边界清晰；出程与回程的风控暴露面被清晰分离。

**负面 / 代价**：

- 每轮多一次人工确认（方案 A 的固有成本，用户已知并接受）。
- 需要实现围栏切分与路径行解析，并承担页面改版打破解析的风险（缓解：以代码围栏为唯一稳定锚点，采集层与解析层解耦）。
- **解析成功率取决于用户自己的提示词写得好不好**——程序不能替用户保证模型按约定回复，这是"只做解析、不替用户表达"的直接代价。

**已知风险**：若用户的格式要求经常不被模型遵守，一键同步的价值会缩水——届时正确做法是改进**用户侧的提示词习惯**（或在 UI 上给出可复制的格式要求文案供用户自己发），**而不是**改为程序注入指令头或授予模型写盘能力。

> 修正记录：本节早期表述为"契约由我们驱动（载荷头部附带指令头）"，并评估过"指令头占用注入预算"的代价。经用户澄清提示词由用户自己写，该方案已废弃。
